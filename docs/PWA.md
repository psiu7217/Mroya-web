# Installing Mroya

The production guest and authenticated chat headers offer installation in the desktop overflow menu and mobile account menu. Mobile browsers additionally show a download icon in the header. Design Mode remains offline and does not register a service worker.

- iPhone/iPad: the action opens a short Share → Add to Home Screen → Add instruction. Embedded browsers can require opening the site in Safari first.
- Android/Chromium: a captured `beforeinstallprompt` opens the system install dialog synchronously from the click. An offer is consumed once. If the browser has not offered installation (including after dismissal), show instructions for its own install menu. Browser installability and engagement rules control when the native offer is available.
- App launch uses standalone display. Both manifests have the same `/` identity/start URL/scope, so changing languages does not create a separate app. The name and Apple title follow the existing language preference: Russian `Мроя`, otherwise `Mroya`. The early HTML script selects the guest manifest; the production hook updates it when confirmed profile language changes. Existing installed launcher names may update on a browser-controlled schedule.
- Icons reuse the current header's `public/brand/mroya-golden-network.png`, including the Apple touch icon.

`appinstalled` and standalone display confirm installation. A non-sensitive local browser hint suppresses repeat promotion on later visits; a new native offer overrides a stale hint after uninstall. Merely opening instructions, accepting a prompt, or dismissing it does not write that hint. Storage denial does not block the UI. iOS does not expose a browser installation event or a reliable API to detect an existing Home Screen app from Safari; standalone launches hide installation controls, but a separate Safari visit can still show them. See [MDN installation behavior](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).

The service worker is network-only. It bypasses API requests and static assets and does not use Cache Storage. A failed same-origin non-API navigation receives a small bilingual offline message with Retry, served with `Cache-Control: no-store`. No personal data or authenticated responses are saved for offline use. Session cookies and the existing API/auth implementation remain authoritative.
